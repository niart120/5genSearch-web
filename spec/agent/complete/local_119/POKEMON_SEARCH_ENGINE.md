# ポケモン条件による起動日時検索 技術設計書

## 1. 概要

### 1.1 目的

[POKEMON_SEARCH.md](../local_118/POKEMON_SEARCH.md) の「色違い・性格から探す」を実現する検索処理、CPU / GPU の実行経路、WASM API を定義する。個体値を条件にせず、指定された日時範囲・起動条件・消費範囲を探索する。検索条件は色違い・性格・出現種・性別・特性・レベルとする。

実装・検証完了（2026-09-06）。`local_120` を PR #169 で先行マージし、その生成器へ日時検索器・Worker・画面を接続した。5 節に検証と性能測定を記録する。

### 1.2 用語定義

| 用語 | 定義 |
|------|------|
| 起動候補 | 日時と単一の `StartupCondition` の組。これから初期 LCG Seed を計算する |
| 消費位置 | `GenerationConfig.user_offset` から列挙する位置。起動時の自動消費 `game_offset` は別に加算される |
| PID | `CorePokemonData.pid` に格納される生成済みの性格値。`nature` とは区別する |
| 直接探索 | 各起動候補から生成した個体に条件を適用する方式。目標 MT Seed 集合を使わない |
| バッチ | WASM の同期呼び出し 1 回で処理し、Worker に制御を返す単位 |

### 1.3 背景・問題（着手時点）

現行には日時から MT Seed を照合する処理と、Seed から個体を生成・絞り込む処理があるが、個体値不問のポケモン条件を日時範囲へ直接適用する処理がない。

| 現行の実装 | 確認した責務・制約 |
|------------|--------------------|
| `wasm-pkg/src/datetime_search/base.rs` | 有効日時を列挙し、`DatetimeHashGenerator.next_quad()` で最大 4 件の SHA-1 計算結果を生成する |
| `wasm-pkg/src/datetime_search/mtseed.rs` | 日時のハッシュから MT Seed を求め、目標集合への所属を判定する。結果は `SeedOrigin[]` |
| `wasm-pkg/src/datetime_search/egg.rs` | 日時から `EggGenerator` を起動して消費範囲を判定する先例。ただし 1 バッチ内で各 Seed の全消費範囲を処理する |
| `wasm-pkg/src/generation/flows/generator/pokemon.rs` | 起動時消費、先頭特性、固定・野生などの分岐を使って個体を生成する。着手時はコンストラクターで MT 側の個体値も計算していた。`local_120` で遅延計算へ変更済み |
| `wasm-pkg/src/types/filter.rs` | 色違い・性格・種族・性別・特性・レベルなどを判定する |
| `wasm-pkg/src/gpu/datetime_search/shader.wgsl` | SHA-1 と MT Seed 照合を行い、一致した日時の情報を返す。ポケモン生成や条件判定は行わない |
| `src/workers/search.worker.ts` | WASM のバッチ間でイベントループに制御を返し、進捗報告・キャンセル受信・解放を行う |
| `wasm-pkg/src/resolve/pokemon.rs` | `GeneratedPokemonData` を表示データへ変換する。起動日時・条件と個体値不明の表示も扱う |

### 1.4 期待効果

| 項目 | 期待効果 |
|------|----------|
| 探索範囲 | 任意に選んだ MT Seed 集合による間引きをせず、指定範囲を探索できる |
| 判定の整合性 | 個体生成リストと同じ生成・フィルター処理を基準にする |
| 結果転送 | 全起動候補を JavaScript に渡さず、一致個体だけを返す |
| 応答性 | 消費範囲の途中でもバッチを終了し、キャンセル受信の機会を設ける |

### 1.5 着手条件

API とバッチ契約に従って実装した。対応エンカウントは固定・野生・徘徊を含む既存の個体生成リストの対応範囲を基本とし、既存のソフト別・生成方式別の制約を継承する。例外が必要な場合は対象と理由を記載する。今回の実装は CPU 経路のみとし、GPU 経路の追加は対象外とする。孵化・MT Seed 検索の API 変更を前提にしない。

[local_120: PokemonGenerator のフィルター統合と個体値遅延計算](../local_120/POKEMON_GENERATION_PIPELINE.md) を先行実装し、既存生成結果の一致と生成器内の段階的判定・個体値遅延計算を検証してから本書の日時検索器へ接続する。

## 3. 設計方針

### 3.1 採用方式: CPU での直接探索

「色違い・性格から探す」は CPU 経路のみで実装する。既存の日時・SHA-1 バッチ生成とポケモン生成を Rust 内で接続し、Web Worker で実行する。

```text
日時範囲 × Timer0/VCount/キー入力
  → DatetimeHashGenerator
  → LCG Seed と SeedOrigin::Startup
  → PokemonGenerator に生成条件とフィルターを渡す
  → generate_next() で一位置を生成・判定
  → Some の完成した一致個体を収集（None でも次の位置へ進む）
  → 一致した GeneratedPokemonData だけをバッチ返却
```

日時生成と個体生成の間で JavaScript に候補全件を渡さない。ランダム MT Seed の生成や全 MT Seed の列挙によって既存の一致検索を代用しない。

候補生成・条件判定・結果完成は `local_120` の `PokemonGenerator` 内部で行う。日時検索器は候補を受け取って判定するのではなく、生成器が返した完成済みの一致個体だけを収集する。新検索の条件はすべて個体値非依存なので、一致のない Seed では MT 計算を行わず、一致した Seed では個体値を一度だけ算出・再利用する。

### 3.2 対抗案と今回の不採用理由

既存 GPU 経路には日時から SHA-1・MT Seed を計算する処理と 64 bit LCG 演算の部品があるが、目標 MT Seed の照合をせずに LCG Seed をバッチ返却する経路や、消費範囲のポケモン生成・条件判定はない。

| 対抗案 | 今回の不採用理由 |
|--------|------------------|
| GPU で起動候補の LCG Seed をバッチ生成し、CPU で個体判定 | 専用の候補出力・転送制御を新設する必要があり、全候補の転送費用も増える。既存の CPU 生成処理を直接接続する範囲を超えるため不採用 |
| GPU で粗く絞り、CPU で正式判定 | 真の一致を落とさない条件の検証が必要。生の LCG 出力だけでは PID 補正・再抽選・生成分岐を代替できないため不採用 |
| GPU で日時から個体判定まで実行 | 起動時消費と各エンカウントの生成・判定を GPU 側に実装する必要があり、ポケモン生成の移植を伴うため不採用 |

「MT Seed(個体値)から探す」は既存の CPU / GPU 経路を維持する。新経路には `useGpu` を流用せず、GPU 切替を設けない。将来の GPU 対応は別途設計し、本書では GPU 用 API や実行時の振り分けを定義しない。

### 3.3 生成順序と追加最適化

生成器内部での段階的判定と MT 計算の遅延は、`local_120` を前提として初期実装に含める。計測後に検討するのは SIMD 化などの追加最適化とする。Seed ごとの初期化、MT 個体値計算、各消費位置の生成、結果変換・転送の費用を分けて評価する。

個体値・実数値は一致個体を返却する前に既存の生成条件で算出する。未計算を理由に不明値を返したり、0 などの仮の確定値を埋めたりしない。生成条件上もともと不明な値は既存の扱いを維持する。同一条件で PID・性格・種族・個体値・実数値・消費位置が既存生成と一致することを検証する。

## 4. 実装仕様

### 4.1 条件と判定

専用型 `PokemonDatetimeSearchFilter` を追加する。個体値・実ステータス条件を型に含めず、六条件を `PokemonFilter` に変換して `PokemonGenerator` に渡す。個体値・実数値・持ち物・発生条件は未指定、出現結果は `PokemonOnly` とする。比較処理は生成器内部の共通フィルターに任せ、日時検索器では再判定しない。

| フィールド | Rust 型 | 意味 |
|------------|-------------|------|
| `shiny` | `Option<ShinyFilter>` | 星・ひし形・色違い全体 |
| `natures` | `Option<Vec<Nature>>` | 性格。複数選択内は OR |
| `species_ids` | `Option<Vec<u16>>` | 実際に生成された種族。複数選択内は OR |
| `gender`、`ability_slot` | `Option<Gender>`、`Option<AbilitySlot>` | 既存の性別・特性スロット条件 |
| `level_range` | `Option<(u8, u8)>` | レベルの閉区間 |

`pid`、`held_item_slots`、`special_encounter_triggered`、移動エンカウント判定のフィールドは専用条件型に含めない。PID は既存の生成・色違いなどの判定・結果データには残し、数値の完全一致検索は提供しない。

性別・特性は生成後の `core.gender`・`core.ability_slot` と比較する。特性スロットを指定しても、そのエンカウントで生成できない特性を生成可能にはしない。`level_range` は上下限を含み、同値による単一レベル指定を許容する。API では上下限の逆転と 1～100 の範囲外を入力エラーにする。UI は既存 `LevelRangeInput` を再利用するため、入力確定時に 1～100 へ収め、上下限を並べ替える。

条件間は AND。任意条件の欠落・空の選択配列は共通フィルターで指定なしとして扱う。全条件未指定も API 上は有効とし、指定範囲のポケモンを列挙する。UI は既存の事前見積もり・件数警告を利用する。

ポケモン検索なので `EncounterResult::Pokemon` を必須とする。釣り失敗やアイテム結果をポケモンの一致結果として返さない。移動・特殊エンカウントの付加情報は既存生成と同じ意味を保ち、生成個体の一致が実機上の遭遇成功を無条件に保証するとは表示しない。

種族条件のために `PokemonGenerationParams.slots` を絞ったり並べ替えたりしない。元のスロット構成で生成した後、`core.species_id` に条件を適用する。性別・特性・レベル条件も生成パラメーターの上書きには使わず、生成後に適用する。

`PokemonGenerationParams` は既存型を維持する。UI は色違い条件が指定され、TID / SID のいずれかが未設定の場合だけ検索を禁止する。色違い指定なしでは ID 未設定を許可し、既存 `pokemon-list-page.tsx` と同じく `tid: trainer.tid ?? 0` / `sid: trainer.sid ?? 0` を生成パラメーターに渡す。設定済みの値は維持し、0 と未設定を入力検証で混同しない。WASM 側は具体的な ID を受け取るため、未設定の検証は UI の検索要求作成時に行う。

ID の補完は既存生成経路への接続規則であり、実際のトレーナーに対する生成結果の保証ではない。ID は PID 補正と色違い判定に使われ、ひかるおまもり使用時は再抽選の終了位置を通じて後続の性格等にも影響し得る。色違い条件を指定しない場合もこの影響は残るが、ID 未設定による検索禁止は追加しない。この制約は仕様上の説明に留め、補完を知らせる専用の警告・注記・表示・出力項目は追加しない。検索後の共通設定変更で過去の生成済み結果を書き換えない。

### 4.2 探索範囲と処理順

起動候補ごとに次の順序で処理する。

1. `DatetimeHashGenerator` から日時とハッシュを取得し、初期 LCG Seed と `SeedOrigin::Startup` を作る。
2. `PokemonGenerator::new(source, pokemon_params, gen_config, filter)` で既存の起動時消費を求め、`game_offset + user_offset` へ進める。この段階では MT 計算を行わない。
3. `user_offset <= advance < max_advance` の各位置で `generate_next()` を呼ぶ。候補生成・判定・必要時の MT 計算・実数値計算はこの呼び出しの内部で行う。
4. `Some(data)` を結果へ格納する。`None` は一位置の不一致または結果なしとして処理件数に数え、終了とはみなさない。
5. 指定範囲を処理し終えたら次の起動候補へ進む。

現行 `generate_pokemon_for_seed` は `max_advance - user_offset` 回生成するため、終了値は含まない。例: `6..30` は 6～29 の 24 位置。同値なら 0 位置として直ちに完了する。UI でも終了値を含まないことを明示し、新経路だけ `+1` して既存と異なる意味にしない。

個体生成では列挙用 LCG の複製を使う既存処理を維持する。ある位置での生成中に消費した乱数数だけ、次の候補位置を進める実装にはしない。`generate_next()` が `None` を返しても、その位置を処理済みとして数える。

### 4.3 WASM API

型は Rust の `types/` で `tsify` + `serde` により定義し、関数・探索器は `lib.rs` の公開経路に追加する。既存 API は維持する。

| API | 契約 |
|-----|------|
| `generate_pokemon_search_tasks(context, pokemon_params, gen_config, filter, worker_count)` | 検証済みの日時・起動条件をタスクへ分割し、`Result<Vec<PokemonDatetimeSearchParams>, JsValue>` を返す |
| `PokemonDatetimeSearcher::new(params)` | `Result<PokemonDatetimeSearcher, String>`。不正入力を生成開始前に拒否する |
| `next_batch(limits)` | `Result<PokemonDatetimeSearchBatch, String>`。日時と消費位置の途中状態を保持して再開する |
| `is_done` | 未処理の日時・消費位置がない場合のみ `true` |
| `free()` | Worker の `finally` で解放する wasm-bindgen のオブジェクト解放 |

`PokemonDatetimeSearchParams` は `ds`、`time_range`、`search_range`、`condition`、`pokemon_params`、`gen_config`、`filter` を持つ。前半は `EggDatetimeSearchParams` と同じ分割単位とする。`ds.version` と `gen_config.version` の不一致はエラーにする。

`PokemonDatetimeSearchBatch` は `results: Vec<GeneratedPokemonData>`、`processed_count: u64`、`total_count: u64` を持つ。結果の `source` は必ず `Startup`。既存の `GeneratedPokemonData` に起動情報が入るため、同じ情報を別の結果構造に複製しない。カウンターは `large_number_types_as_bigints` で公開し、Worker の既存 `calculateProgress` で number に変換して進捗基盤へ渡す。

`PokemonSearchBatchLimits` は次を持つ。

| フィールド | 意味 | 採用値 |
|------------|------|----------------|
| `max_candidates: u32` | 1 回で判定する消費位置数の上限 | 1,024 |
| `max_results: u32` | 1 回で返す一致個体数の上限 | 256 |

いずれも 1 以上を要求する。上限は結果を捨てるためのものではなく、その位置でバッチを返して続きへ進むための制限である。調整値は実測で変更してよく、探索結果に影響させない。

### 4.4 バッチ状態・進捗・検証

探索器は日時生成器に加え、`next_quad()` で取得済みの未処理日時、現在の `PokemonGenerator` を保持する。生成器内の消費位置・`rng_ivs` もバッチをまたいで保持する。上限に到達したらそれらを残して返し、次回は次の未処理位置から再開する。4 件まとめて取得した残りの日時を捨てない。

進捗単位は「起動候補 × 消費位置」とする。各タスクの有効日時数を N、消費位置数を A とすると、`total_count = N × A`、`processed_count` は成功・失敗を含め実際に判定した位置の累計である。計算は検査付き `u64` とする。

N は分割範囲と時刻条件の正確な共通部分から計算する。部分日を丸一日と数える近似は使わない。A = 0 または N = 0 は結果なしで完了する。Rust のタスク内カウンターは単調増加し、正常終了時に処理済み数と総数が一致する。

全体進捗は既存の `runSearchLoop`、`calculateProgress`、`ProgressAggregator`、`useSearch` と表示部品を利用する。`ProgressInfo` / `AggregatedProgress` の件数は number のままとし、報告済みタスクを集計する既存方式を維持する。タスク生成 API に総数通知用の型・フィールドを追加せず、全タスクの総数を開始時に事前登録しない。number 変換後の整数精度と全体進捗率の単調増加は今回の保証に含めない。これらは進捗表示上の扱いであり、Rust の探索範囲・終了判定・結果収集には使用しない。

日時は暦日として 2000～2099、時刻は有効範囲、消費範囲は `user_offset <= max_advance < u32::MAX` を要求する。空スロット、固定の複数スロット、種族 1～649・レベル 1～100 以外、版不一致、起動設定、非対応エンカウントを開始時に拒否する。起動時消費は Seed に依存するため、`game_offset + max_advance` の検査付き加算は各 Seed の生成器初期化時に行う。先頭 Seed は検索器のコンストラクター、後続 Seed は `next_batch` でエラーを返す。新しい日時検索 API の入力エラーと生成器の初期化エラーは検索エラーとして返す。初期化後の `generate_next()` の `None` は `local_120` の一位置を処理した契約に従い、API の入力エラーや列挙終了とは区別する。

### 4.5 Worker と結果表示

UI の配置は `local_118/POKEMON_SEARCH.md` の 4.1 に従う。既存 MT Seed セクションの位置に方式切替を置き、色違い・性格側を選択した場合に本書の検索器へ接続する。日時・キー入力は既存の位置を維持し、選択方式に対応する保存値を利用する。検索操作・検証・見積もり・結果表示も選択方式へ連動させ、非選択側の入力や結果を混在させない。

`createPokemonDatetimeSearchTasks` から WASM のタスク生成を呼び、`kind: 'pokemon-datetime'` の CPU タスクを作る。既存の組み合わせ展開・日時分割・WorkerPool を利用し、SharedArrayBuffer や WASM threads は導入しない。

`search.worker.ts` の共通 `runSearchLoop` に接続し、各バッチ後にキャンセルを受信可能にする。これは既存の協調的キャンセルの継続であり、中断までの時間保証は非機能要件に設けない。日時列挙の走査予算や時間制限 API は今回追加しない。

既存 Worker 応答は `resultType` を持つが、WorkerPool は結果配列のみを通知し、機能別フックが配列を取り出して Store に同期している。今回の返却データは既存ポケモンリストと同じ `GeneratedPokemonData[]` なので、既存の `PokemonListResultResponse`（`resultType: 'pokemon-list'`）を再利用する。タスクの `kind: 'pokemon-datetime'` は探索処理の選択に必要だが、結果種別タグを新設する理由にはしない。WorkerPool の `SearchResult` に `GeneratedPokemonData[]` を明示的に含め、既存ポケモンリストの配列収集処理を利用する。タグをフックまで維持する共通基盤の再設計は、本機能の前提に含めない。

結果は検索開始時の条件のスナップショットと結び付ける。既存 WorkerPool の taskId による受信判定を利用し、古いタスクの応答が新しい検索へ混入しないことを検証する。

個体生成リストへの転記は `local_118/POKEMON_SEARCH.md` の 4.4 に従い、結果詳細で選択した 1 件だけを対象とする。結果の `source` と検索開始時の対象・生成条件を組にして渡す。場所キー・固定対象 ID など WASM の生成結果だけでは復元できない画面側の対象選択情報も、検索開始時のスナップショットに保持する。転記先ではエンカウント種別・対象選択・遭遇方法・スロット・先頭特性を反映し、既存のフィルターと `user_offset` / `max_advance` は保持する。転記による自動生成と新方式の全結果転記は行わない。

起動情報の受け取りは既存の詳細転記経路に合わせる。渡された日時・キー入力を用い、転記先の現在の本体設定と Timer0 / VCount 範囲で Seed 候補を再計算する。選択した結果の Seed と起動条件を固定した入力方式には変更しない。転記操作の対象は結果 1 件だが、再計算後の Seed 候補が 1 件になるとは限らない。共通設定を検索時の値へ復元する機能は追加しない。

結果の表示は既存の `resolve_pokemon_data_batch` と個体生成リストの表示境界を利用する。個体値・実数値を表示・エクスポート対象とし、表示モードや CSV / JSON の出力規則も既存の個体生成リストに揃える。個体値不問であることを理由に値を削除しない。値は既存の生成・計算条件に基づくものとし、実機側で異なる MT 消費が発生した場合まで一致を保証する意味は持たせない。

結果収集の総件数上限と上限による自動停止は設けない。既存検索と同様に、開始前の推定結果件数が `DEFAULT_RESULT_WARNING_THRESHOLD`（現行 50,000 件）を超える場合は `SearchConfirmationDialog` で確認し、続行を選べばその条件で検索する。確認対象の検索条件を保持し、確認後に別の条件を読み直さない。`max_results` は一バッチの返却件数であり、検索全体の上限ではない。終了・手動中断・エラーと受信済み結果の保持は既存の検索フックに合わせ、上限停止専用の状態は追加しない。

新しい日時検索の見積もりは「全起動候補数 × 消費位置数 × 概算一致率」とする。既存の `estimatePokemonListResults` の考え方を利用するが、シンクロ・色違い制御等により一致率は生成条件に依存する。採用した概算率は性格数 / 25、性別・特性は各 1/2、色違い全体・星・ひし形は各 8/65536・7/65536・1/65536 の積。種族・レベルは反映せず、シンクロ・性比・色違いロック・ひかるおまもり・遭遇失敗を補正しない。既存の独立確率モデルを用いる事前警告であり、過大・過小の双方の誤差があり得る。推定件数は正確な進捗総数とは区別する。

### 4.6 タスク分割と対応範囲の決定

既存 `expand_combinations` の範囲ごとの展開を維持し、重複除去は追加しない。重なる範囲では同じ起動条件の結果が複数回得られる。日時チャンクの境界重複はテストで除外する。

新 API は空・逆転した Timer0 / VCount 範囲と Worker 数 0 を入力エラーにする。既存の卵・MT 検索や `WorkerPool.start([])` は変更しない。時刻条件との共通部分 N = 0 または A = 0 の有効タスクは、総数・処理数 0 の進捗を返して正常終了する。

`Normal`、`ShakingGrass`、`DustCloud`、`PokemonShadow`、`Surfing`、`SurfingBubble`、`Fishing`、`FishingBubble`、`StaticSymbol`、`StaticStarter`、`StaticFossil`、`StaticEvent`、`Roamer` を既存の生成器へ接続する。`HiddenGrotto` は既存共通生成器のディスパッチ対象外であり、今回も明示的な非対応エラーにする。`Egg` は孵化検索の対象とする。ソフト別の対象候補は既存の `PokemonParamsForm` とデータローダーに従う。

### 4.7 計算量と評価計画

起動候補数を N、消費位置数を A、一致がある起動候補数を H、一致個体数を R とすると、費用は概ね `N × (SHA-1 + 起動時初期化 + A × 候補生成・判定) + H × MT 個体値計算 + R × 結果完成` である。個体生成内の再抽選などにより一位置の費用は一定ではない。

| 測定項目 | 比較条件・目標 |
|----------|----------------|
| 正しさ | 同じ有限範囲で既存一括生成後の条件適用と結果集合が一致する |
| 探索速度 | 起動候補数 N = 1,000 / 10,000、A = 30 / 1,000 / 10,000 を基準に、徘徊・固定・野生を個別測定する |
| 条件の違い | 色違い、性格、種族、性別、特性、レベル、無条件で生成と結果転送の費用を分離する |
| バッチ応答 | 1 回の同期処理時間を測定し、代表端末で 100 ms 以下を調整目標とする。現時点の保証値ではない |
| メモリー | 一致なし・大量一致の双方でピークを測定。未一致候補の全件保持がないことを確認する |
